01Auth / RBAC Бэкенд-лид▶
Реализовать JWT-авторизацию и ролевую модель доступа. Все роли и права хранятся в БД — администратор меняет без деплоя. Каждое действие логируется: кто, что, когда.

Принимает логин и пароль, возвращает токены. В ответе сразу список permissions — фронт строит меню на его основе, без отдельного запроса.

02Заявки (Applications) Backend Dev #1▶
Центральная сущность. Жизненный цикл со строгой матрицей переходов — каждый переход логируется с автором и временем. Два ключевых требования: (1) автоотмена если клиент не подписал за 24 ч, (2) одобрение на альтернативную меньшую сумму с пересчётом условий.

PATCH/applications/{id}/approveNew
Одобрение заявки. Если approved_amount ≠ requested_amount — пересчитываем вознаграждение и ГЭСВ. После одобрения запускается таймер 24 ч.
Бизнес-правила
  • approved_amount ≤ requested_amount — нельзя одобрить больше чем запросил клиент
  • approved_amount не ниже min_amount продукта
  • После одобрения — SMS клиенту со ссылкой на подписание
  • sign_expires_at = now() + 24h — CRON проверяет каждые 10 минут

04Платежи (Payments) Backend Dev #2▶
Два источника: вебхук от платёжных организаций и CSV-выписка из 1С. Несовпавшие по ИИН — в очередь для ручной привязки. Только полное погашение. Пеня — CRON ежедневно.
POST/payments/webhook
Вебхук от платёжных организаций. Идемпотентность по transaction_id обязательна — дубль игнорируется с ответом 200.
Бизнес-правила
  • Проверить transaction_id на дубль перед записью
  • Сопоставить по ИИН с активным займом клиента
  • Платёж ≥ остатка долга → статус займа CLOSED
  • ИИН не найден → записать как unmatched, уведомить финаналитика

ПолеТип

Загрузка CSV-выписки из 1С. Авто-сопоставление по ИИН. Несовпавшие строки → unmatched_items для ручной привязки.
